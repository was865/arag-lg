# 034 実際の規模の模擬の業務データ — 設計

状態: **承認済み（2026-11-20）**。

## 1. 全体

```
sim/（uv の別プロジェクト。mock/systems と並ぶ）
  world.py      会社の骨格: 部品・仕入先・顧客・社員・部門・倉庫・設備（固定の表 + 種から作る部分）
  rules.py      需要（受注の発生）・季節・リードタイム・発注点の規則・遅れや取り消しの起こり方
  run.py        2026-04-01〜2026-11-18 を 1 日ずつ進め、出来事（Event）を出す
  sinks/
    sqlite.py   032 の模擬の表に書く（在庫などは模擬器が計算）
    odoo.py     Odoo の API で業務の流れとして入れる（在庫は Odoo が計算）
  docs/         ある時点の文書を作る（openpyxl・python-docx・PDF）
  answers.py    題の正しい答えをスナップショットへの問い合わせで計算する
```

- 出来事は小さな型（`PurchaseOrdered`・`Received(partial)`・`Issued`・`Scrapped`・`SalesOrdered`・`Shipped`・
  `PriceChanged`・`WorkRecorded`・`WorkOrderOpened/Closed`）。2 つの出力先は同じ出来事の列を受け取る（R6）。
- 種: `SIM_SEED`（既定 20261118）。同じ種・同じ版の規則なら同じ出来事の列（R5）。

## 2. 今の harukaze を含める（R1・R14）

- 今の 8 部品・3 仕入先・9/30 の在庫・10 月〜11 月の動き（032 の `seed.py`）は **固定の出来事** として最初に入れ、乱数で動かさない。
- 新しく足す部品・仕入先は、今の部品番号・仕入先コードと重ならない帯（P-5000 番台〜・S-20 番台〜）を使う。
- 確かめ: 大きい世界の SQLite で harukaze_systems を流し、032 の結果と同じ答えになること（契約のテスト）。

## 3. 本物らしさの規則（R3・R4）

| 乱れ | 作り方 |
|---|---|
| 分けて届く入荷 | 発注の 15% は 2〜3 回に分けて入る |
| 納期の遅れ | 仕入先ごとの遅れやすさ（海外は大きい）で、5〜20% が遅れる |
| 取り消し・数量の変更 | 発注の 3% |
| 単価の変化 | 仕入先・部品ごとに四半期で ±0〜8%。標準単価は年に 1 度だけ改める |
| 似た名前 | 軸受・シール・羽根車に枝番と仕様違い（C3・2RS など） |
| 廃止と後継 | 10 部品に廃止の日と後継を持たせる（KG-2 → KG-5 と同じ形） |
| 呆滞・見本の倉庫 | 一部の在庫を使えない倉庫に置く（使える在庫に数えない） |
| 単位 | ボルト・ナットは箱（100 個）、グリスは kg と缶の両方 |
| 雑な備考 | 決まった文の型からいくつかを組み合わせる（指示に見える文は 032 と同じく 1〜2 件だけ） |

- 受注は顧客ごとの月の需要に季節の波を掛けて発生させ、出庫は受注と保全の作業から決まる。
  発注点を下回ったら規則どおり発注する（担当の遅れ・忘れも少しだけ起こす）。

## 4. Odoo に入れる（R6・R7）

- `stock.picking` の完了の日付（`date_done`）や `stock.move` の日付を過去にできるかは、最初に実測する（T2）。
  - できる場合: 出来事の日付で入れる。
  - できない場合: 模擬器の日付を Odoo の `date` などの書ける項目に入れ、完了の日付は流した日になることを設計に追記し、
    答えの計算（answers.py）は書ける項目のほうを使う（黙って日付をずらさない。R7）。
- 入れ終えたら `pg_dump`（033 の `make erp-reset` が戻す）。大きければ git に入れず、作り方（`make sim-odoo`）と sha256 だけを置く。

## 5. 文書（R8〜R10）

- 生成する文書（新しいファイルだけ）: 第二工場の部品台帳（10 月末）・月次報告 10 月（pptx）・在庫の報告（xlsx・週ごと）・
  品質会議の議事録 10 月・11 月（docx）・仕入先の評価（pdf）。
- 手で書く: 第二工場の規程の補足・倉庫の使い分けの決まり。食い違いを 3〜5 か所入れ、`conflicts.yaml` に書く。
- 文書の作成の依存（openpyxl・python-docx・PDF を作るもの）はライセンスを確かめて `licenses.md` に書く（sim は評価用で製品に含めない）。

## 6. 答えの計算と題集（R11〜R13）

- `answers.py` は、題ごとの問い合わせ（例 「今、発注点を下回っている部品」= 使える倉庫の在庫 < 発注点）をスナップショットに対して流し、
  `key_facts` と根拠（どの表のどの行か）を題集の下書きに書く。
- 題集 `eval/suites/harukaze_plant/golden.yaml`（40 題前後）。題は 1 問ずつ確かめて確定する（根拠を見せる）。
- 大きい結果の題（例 「納期を過ぎた発注を全部」= 40 件）で、032 の切り詰め（50 行・8,000 字）とページ送り（033 R5）の振る舞いを見る。

## 7. 採否

- 模擬器は Python（評価の側の道具。製品の依存にしない）。乱数は `random.Random(seed)` だけを使う。
- 生成した文書は KB に入れて使う（ingest の経路を通る。解析の点検 030 で見える）。
