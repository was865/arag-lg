# 034 実際の規模の模擬の業務データ（模擬器・文書の生成・スナップショット）— 要件

状態: **承認済み（2026-11-20）**。

## なぜやるか

032 の模擬のデータは 8 部品・発注 3 件で、評価の再現には足りるが、本物らしさが足りない。
ページ送り・似た名前・時間とともに変わる単価・分けて届く入荷・止まっている倉庫など、実際の工場のデータで起きることが無い。
033 で本物の ERP（Odoo）を立てても、中身が小さければ確かめられることは少ない。

そこで、評価資料の会社（株式会社ハルカゼ精工・浜松第二工場）を **そのまま広げた** 世界を作る。
今の文書と値（harukaze_mix 69 題・harukaze_systems 30 題が頼るもの）は変えず、その周りに、システムにしか無い大量のデータを足す。
実際の会社でも、文書が覆うのは業務のごく一部で、ほとんどはシステムにしか無い。

## 1. 世界の広さ

- R1. 模擬のデータは、今の harukaze の文書と値（9 月 30 日の部品台帳の 8 部品・保守記録・議事録など）を変えず、そのまま含む。
- R2. 模擬のデータは、次のくらいの規模を持つ: 部品 300〜500・仕入先 30・顧客 40・社員 60・部門 6〜8・工場 2・倉庫 4（使える倉庫・呆滞・見本・第二工場）・
  2026 年 4 月〜11 月の発注約 1,500・入出庫約 10,000 行・受注約 800・作業の記録と作業指示約 300。
- R3. 模擬のデータは、本物らしい乱れを含む: 分けて届く入荷・納期の遅れ・取り消し・数量の変更・時間とともに変わる仕入単価・
  標準単価と仕入単価の違い・似た名前の部品（6308ZZ ／ 6309ZZ ／ 6308ZZ-C3）・廃止と後継・単位の混在（個・箱・kg）・
  空の項目・日本語と英語の名前・海外の仕入先・人の書いた雑な備考。
- R4. 模擬のデータの値は、需要と季節・リードタイム・発注点の規則から決まり、乱数だけで決めない（数字のつじつまが合う）。

## 2. 作り方

- R5. システムは、日ごとに業務を進める模擬器を持つ。模擬器は種（seed）が同じなら毎回同じ世界を作る。
- R6. 模擬器は、出力先を差し替えられる: Odoo（033）には業務の流れ（発注 → 承認 → 入荷 → 出庫）として API で入れ、ERP が在庫を計算する。
  032 の模擬（SQLite）には同じ結果を表として書く。2 つの出力は同じ問いに同じ値を返す。
- R7. Odoo に過去の日付で入れられない項目があるとき、模擬器はその項目の扱い（実際の日付で動かしてからスナップショットにする等）を
  設計に書き、黙って日付を変えない。

## 3. 文書

- R8. システムは、模擬のデータのある時点から、文書を生成できる（部品台帳・月次報告・在庫の報告・品質会議の議事録。xlsx・docx・pdf）。
  文書の値は、その時点のデータと一致する。
- R9. 規程・手順書のような変わらない文書は手で書き、その一部に、システムと食い違う古い記述（例 古い内線・古い単価）を含めてよい。
  食い違いは一覧（`eval/assets/<suite>/conflicts.yaml`）に書く。
- R10. 今の harukaze_mix の文書は生成し直さない（R1）。新しい文書は新しいファイルとして足す。

## 4. スナップショットと評価

- R11. 模擬器を流し終えたら、その状態をスナップショット（Odoo は `pg_dump`、模擬は SQLite のファイル）として固め、
  評価の前に毎回戻せる（評価を再現できる）。
- R12. 題の正しい答えは、スナップショットに対する問い合わせ（コード）で計算して題集に書く（手で書いた数字を使わない）。
  題そのものは 018 R5 と同じく 1 問ずつ確かめて確定し、確かめるときに計算の根拠を見られる。
- R13. 大きい世界の題集（`harukaze_plant`、40 題前後）を作る: ページ送り（多い結果）・似た名前・時点の違い・分けた入荷・
  単価の変化・倉庫の使い分け・文書とシステムの食い違い・権限。
- R14. 小さい題集（harukaze_mix・harukaze_systems）は、大きい世界でも同じ答えになる（R1）。違ったら模擬器の誤り。

## 入れないもの

- 本物の会社のデータの取り込み。
- 会計（仕訳・決算）。
