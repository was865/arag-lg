# 033 本物の ERP（Odoo）につなぐ ERP の MCP サーバ — 要件

状態: **承認済み（2026-11-20）**。

## なぜやるか

032 で社内システムを MCP でつなぐ仕組みと評価はできた。ただ、相手は手で書いた小さな模擬（8 部品・発注 3 件）で、
本物の ERP で起きること（業務の流れから値が決まる・API の癖・ページ送り・権限の仕組み・遅さ・項目名の不統一）は確かめられない。
本物の ERP は手元に無いので、オープンソースの ERP **Odoo（Community 版）** を「本物の ERP」として立て、
その前に正式な ERP の MCP サーバを置く。ERP を替えるときは差し替え部品（アダプタ）と項目の対応表だけを替える形にする。

確かめたいこと:

- 業務の流れ（発注 → 承認 → 入荷 → 出庫）で ERP が決めた値を、エージェントが今の値として正しく読めるか。
- 権限を ERP の側で決めても（利用者ごとの見え方の違い）、漏れずに答えられるか。
- ページ送り・遅さ・止まったときに、黙って間違えないか。
- デモで、Odoo の画面で業務を動かすと、その直後の質問の答えが変わるか（「今の値」の実感）。

旧プロジェクト（a-rag の「回交期」、金蝶の MCP の実測）で分かったこと（工具が広すぎる・過滤串の注入・ページ送りの打ち切り・
権限の壁・データ源での伏せ字・書き戻しの護り）を最初から設計に入れる。

## 1. ERP の MCP サーバ（`mcp/erp/`）

- R1. システムは、ERP の MCP サーバを ARag とは別のサービス（uv の別プロジェクト・別の容器・別の鍵）として持つ。
  ERP の接続の鍵（Odoo の API キーなど）は MCP サーバだけが持ち、ARag は URL と身元の署名鍵だけを持つ。
- R2. MCP サーバは、業務の単位のツール（部品・在庫・入出庫・発注・受注・仕入先・設備の保全）だけを出す。
  汎用の検索・SQL・項目名を自由に指定する問い合わせ・書き込みのツールは出さない。
- R3. ツールの入力は型付き（JSON Schema。列挙・日付の形・件数の上限）で、出力は 032 と同じ形
  （`columns`・`rows`・`total`・`fetched_at`・`basis`・`restricted`・`note`）に、続きの手がかり（`next_cursor`）と
  呼び出しの記録（`trace`）を足したものとする。
- R4. MCP サーバは、ERP への問い合わせの条件を、利用者の入力を文字列としてつながず、コードが組み立てる（注入を防ぐ）。
- R5. ERP の結果が複数のページにわたるとき、MCP サーバは上限まですべて取り、上限を超えたら黙って切らずに
  「多すぎる」と返す（件数と、絞り込みの手がかりを添える）。
- R6. MCP サーバは、ERP ごとの差し替え部品（アダプタ）を通して ERP を読む。最初は **Odoo** と **模擬**（032 の SQLite）の 2 つ。
  どちらも同じツール・同じ出力の形を返し、同じ契約のテストを通る。
- R7. ERP ごとの項目の対応（モデル名・項目名・倉庫の扱い・単位）は設定ファイルに書き、コードに埋めない。

## 2. 身元と権限

- R8. MCP サーバは、ARag の身元の JWT（032 と同じ。`aud`・期限・鍵の版 `kid`）を確かめ、無い・不正なら何も返さない。
- R9. MCP サーバは、身元の部門から ERP の利用者（Odoo では部門ごとの技術用の利用者）を選び、その利用者として ERP を読む。
  見せる行・列は ERP の権限で決まる（例: 製造課の利用者は発注の仕入単価を読めない）。
- R10. ERP の権限で読めなかった項目・記録があるとき、MCP サーバはそれを `restricted` と `note` で返し、値を推測で埋めない。
- R11. MCP サーバは、呼び出しごとに監査の記録（利用者・部門・ツール・引数・件数・所要時間・結果の種類）を残す。

## 3. 運用の振る舞い

- R12. MCP サーバは、ERP への呼び出しに待ち時間の上限・同時に投げる数の上限・続けて失敗したら一時的に止める仕組みを持ち、
  止めている間は「ERP が応答しない」とすぐ返す。
- R13. MCP サーバは、同じ利用者・同じツール・同じ引数の結果を短い時間（既定 10 秒）だけ使い回してよい。
  使い回した結果には、元の取得の時点を書く。
- R14. MCP サーバは、死活の確認の口（ERP までつながるか・所要時間）を持つ。
- R15. ARag は、MCP サーバへの接続（HTTP の接続）を使い回し、呼び出しのたびに作り直さない。

## 4. 画面（今の値の実感）

- R16. システムの結果（出典のカード・右の面）は、取得の時点を「12 秒前」のように経過で出し続け、時刻も添える。
- R17. 利用者が「最新にする」を押したとき、システムは同じツール・同じ引数を同じ利用者の身元で呼び直し、
  変わった値を前の値と並べて示す（例 在庫 15 → 14）。呼び直しは記録（システムの処理 `mcp_refresh`）に残す。
  回答の文そのものは書き換えない（書き換えたいときは利用者が聞き直す）。
- R18. エージェントがシステムに問い合わせている間、画面はシステム名・ツール・引数と経過の秒を出し、終わったら件数と所要時間を出す。
- R19. 入力欄の近くに、この利用者が使える社内システムと、それぞれの接続の状態（応答あり・遅い・止まっている）を出す。
  状態は実際の死活の確認の結果で、作った動きは出さない。
- R20. 回答が同じ項目について文書の値とシステムの値を書いたとき、画面はそれを時点付きで並べた小さな比較の表として出す
  （例 部品台帳 9/30: 6 個 ／ ERP 11/18 10:32: 15 個）。
- R21. 管理画面の「社内システム」は、システムごとの直近 1 時間の呼び出しの数・失敗の率・所要時間（p50/p95）と、最近の呼び出しを出す。

## 5. 書き戻し（この仕様では設計だけ。実装は別の仕様）

- R22. 書き込みは、エージェントが自由に呼べるツールにしない。エージェントは「提案」だけを作り、利用者が画面で確かめて押したときだけ、
  別の口で 1 項目だけを書く。書く前の値を確かめ（楽観的な排他）、書く前の値を残し、監査に残す。

## 6. 評価とデモ

- R23. Odoo の環境は compose の profile（`erp`）で立ち、種のデータ（034）を入れた状態のスナップショットから毎回同じ状態に戻せる。
- R24. 評価の題集を、模擬のアダプタと Odoo のアダプタの両方で流せる。Odoo で値が違う題は、違う理由を題集に書く。
  （実装で harukaze_systems から harukaze_plant（034）に替えた。Odoo に入れたのが 034 の世界のため。design §11）
- R25. デモの台本（5 分）を `docs/demo-erp.md` に書く: 文書だけの質問 → 今の値 → 部門で見え方が違う → Odoo の画面で発注を作って聞き直す →
  Odoo を止める → 最新にする。

## 7. ライセンス

- R26. Odoo（Community 版、LGPL-3.0）は評価・デモ用の外部のシステムとして使い、製品に含めず、製品のコードから読み込まない。
  その判断を `specs/000-overview/decisions.md` と `licenses.md` に書く。ERP の MCP サーバの依存は、これまでと同じ基準（MIT・Apache-2.0・BSD）で選ぶ。

## 入れないもの

- 金蝶・SAP のアダプタ（形は決めておく。SAP は API Business Hub のサンドボックスで OData の形だけを後で確かめる）。
- 書き戻しの実装（R22 は設計だけ）。
- 利用者ごとの ERP の利用者（SSO で本人として読む形）。部門ごとの技術用の利用者に限る。
