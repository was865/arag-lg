# 003 入庫（P1）— 要件

`docs/handoff.md` 第 3 節 P1。完了基準: **旧版の評価用 PDF 7 件（`a-rag/rag/eval/assets/agentic_rag_demo/`）が入庫でき、子チャンクと親セクションを API で引ける**。検索・回答は P2 以降。

前提: `specs/000-overview/{features,data-model,api}.md`、`specs/001-p0-skeleton/`。認証は P4（Better Auth）。P1 では開発用の利用者指定（R2）で代替する。

## 1. 利用者と権限

- R1. システムは各要求の利用者を `Principal{user_id, role(owner|admin|member), email_verified}` として扱い、KB の権限判定はすべてこの値から行う。
- R2. `ARAG_AUTH_MODE=dev` のとき、システムは `X-Dev-User-Id` / `X-Dev-Role` ヘッダから Principal を作る。それ以外のモードでヘッダが来ても無視し、Principal が無ければ 401 を返す（P4 で JWT 検証に置き換える）。
- R3. 利用者が初めて KB 一覧を取得したとき、システムはその利用者の個人 KB を 1 つだけ自動作成する（並行要求でも重複しない）。
- R4. 全社 KB は admin（owner を含む）だけが作成・名前変更・アーカイブ・削除・復元できる。全社 KB への書込（アップロード・文書削除・フォルダ操作）は admin のみ、閲覧は全員。
- R5. 個人 KB は所有者だけが閲覧・書込できる。admin であっても他人の個人 KB は閲覧できない（P5 の退職処理を除く）。
- R6. 権限の無い KB・フォルダ・文書・ジョブへの要求には、存在を推測させないよう 404 を返す。

## 2. アップロードと重複排除

- R7. 利用者が KB へ 1〜N 件のファイル（任意で相対パス）を multipart で送ったとき、システムは各ファイルの SHA-256 を計算し、文書ごとに `{document_id, job_id|null, status: queued|skipped|duplicate}` を返す。
- R8. 同じ内容（同じハッシュ）が既に解析済みのとき、システムは解析をやり直さず、新しい文書参照だけを作る（`skipped`）。同じ KB に同じ内容が既にあるときは新規作成せず既存の document_id を返す（`duplicate`）。
- R9. 同じ内容の初回アップロードが同時に複数来ても、原本の保存とジョブ作成は 1 回だけ行う。
- R10. 相対パス付きで送られたとき、システムはパスのディレクトリ部分に対応するフォルダを KB 内に（無ければ）作り、文書をそこに置く。表示名はファイル名部分だけにする。
- R11. 対応形式（PDF / DOCX / XLSX / PPTX / DOC / XLS / PPT / RTF / ODT / ODS / ODP / HTML / Markdown / TXT / CSV / JSON / PNG / JPEG / TIFF / WEBP）以外は 415 で拒否する。1 ファイルの上限（既定 200 MB、設定可）を超えたら 413。
- R12. 原本は内容ハッシュをキーにしたストレージ（`specs/000-overview/data-model.md` §6）へ保存する。

## 3. 入庫パイプライン

- R13. 入庫ジョブは HTTP 要求と切り離したワーカーで実行し、段階 `parsing → chunking → contextualizing → embedding → indexing → ready` を順に進める。段階が変わるたびに `ingest_jobs` の stage・progress（0〜100）・stage_detail（日本語）を更新する。
- R14. 解析は Docling（docling-serve の HTTP API）で行い、結果の DoclingDocument（JSON）・プレビュー用 Markdown・ページ座標・抽出画像をストレージに保存する。
- R15. PDF が設定ページ数（既定 20）を超えるとき、システムはページ窓ごとに分けて解析し、結果を 1 つの文書に結合する（メモリ上限の制御）。
- R16. 旧 Office 形式（DOC / XLS / PPT / RTF）は docling-serve 側の LibreOffice 変換で処理する。テキスト系（TXT / JSON）は Docling を通さず直接テキストとして扱う。
- R17. チャンク化は見出し階層に沿って **親セクション**（章・節。上限 既定 2,000 トークン）と **子チャンク**（検索単位。上限 既定 512 トークン、埋め込みモデルのトークナイザで数える）の 2 層を作る。表が子チャンクの上限を超えて分割されるとき、各片に表ヘッダを繰り返す。
- R18. 各子チャンクには、見出しパス・ページ範囲・ブロック種別（text / table / figure / code / formula / list）・所属セクションを記録する。
- R19. 画像は表示専用として保存し、ベクトル化しない。画像説明の生成が有効なとき、システムは視覚対応モデルで図の日本語説明（図中の文字・流れ・部品名を含む）を作り、`figure` 種別の子チャンクとして索引に入れる。無効または失敗時は、図のキャプションと周辺テキストだけを使う。
- R20. 文脈付与が有効なとき、システムは子チャンクごとに安価モデルで「この塊は〈文書名〉の〈章〉で〜を述べている」形式の 1〜2 文（日本語）を作り、`chunks.context` に保存する。ベクトル化と BM25 の入力は `context + 本文`。無効または失敗時は `文書名 > 見出しパス` を context とする（入庫自体は失敗させない）。
- R21. 文脈付与は 1 文書の中で文書本文をプロンプト先頭の共通部分に置き、プロバイダのプロンプトキャッシュが効く順序で呼ぶ。1 文書あたりの入出力トークン数と費用見積をジョブに記録する。
- R22. 埋め込みは TEI（dense）で、BM25 sparse は Sudachi の分かち書きから自前で作り、両方を 1 つの Qdrant 点に入れる。英数字の型番・条項番号（例 `MX-17`、`第12条の2`）は分割されずに 1 語として残る。
- R23. Qdrant の点の payload には、参照している文書 ID と KB ID の一覧を持たせ、文書の追加・移動・削除・復元のたびに更新する。

## 4. 失敗・再試行・取消

- R24. ジョブが失敗したとき、システムは最大 3 回（設定可）まで指数バックオフで自動再試行し、超えたら `error` で確定してエラー内容（利用者向けの日本語要約と、ログ用の詳細）を残す。
- R25. 同じ内容のジョブを再実行するとき、システムは前回の途中成果（チャンク行・Qdrant 点）を消してからやり直す（冪等）。
- R26. 利用者が `error` のジョブに再試行を要求したとき、システムは回数をリセットして再投入する。`queued` / 実行中のジョブに取消を要求したとき、システムは次の段階に進む前に中断し、`cancelled` にする。
- R27. ワーカーが異常終了したとき、システムは再起動時に途中のジョブを `queued` へ戻して再投入する。
- R28. 外部サービス（docling-serve・TEI・LLM）が応答しないとき、要求ごとのタイムアウト（設定可）で失敗として扱い、R24 の再試行に乗せる。

## 5. 進捗の通知

- R29. 利用者が複数ジョブの ID を指定して進捗ストリームを開いたとき、システムは 1 本の SSE で各ジョブの `{job_id, document_id, stage, progress, stage_detail, status, error?, page_count?, chunk_count?}` を変化時に送り、全ジョブが終端（ready / error / cancelled）になったら閉じる。
- R30. 利用者は自分に閲覧権限のあるジョブの進捗だけを受け取れる。

## 6. 文書・フォルダ・ごみ箱

- R31. 利用者は KB 内の文書をフォルダ・状態で絞り込み、カーソルで一覧できる。各文書には状態・ページ数・チャンク数・書込可否を含める。
- R32. 利用者（KB 書込権限）はフォルダの作成・名前変更・移動・削除・復元と、文書の名前変更・フォルダ移動・一括移動ができる。同じ親の下に同名の生存フォルダは作れない（409）。フォルダを自分の子孫の下へ移動しようとしたら 400。
- R33. 文書・フォルダ・KB の削除はごみ箱送り（`deleted_at`）とし、検索・一覧から除外する。フォルダ削除は配下のフォルダと文書にも及ぶ。復元したとき、削除済みの祖先フォルダも生き返らせる。
- R34. 完全削除は、アップロード本人なら削除後 24 時間以内、admin ならいつでもできる。それ以外は 403。
- R35. ごみ箱に入って保持期間（既定 30 日）を過ぎたものは、ワーカーの定期処理が物理削除する。どの文書からも参照されなくなった内容（ref_count = 0）は、原本・成果物・チャンク・Qdrant 点まで削除する。
- R36. 削除・復元・完全削除・GC は監査ログ（`audit_logs`）に記録する。

## 7. 参照（プレビュー・検証用）

- R37. 利用者は文書の原本（Range 要求対応）、解析済み Markdown、見出しツリー（親セクション一覧）、セクション本文、子チャンク一覧、抽出画像を取得できる。
- R38. 見出しツリーの各節には、ページ範囲と子チャンク数を含める。

## 8. 運用

- R39. 全処理のログに `request_id`（API 起点）または `job_id`（ワーカー）が付く。
- R40. `/readyz` に docling-serve の疎通を加える（未設定なら skipped）。
- R41. 埋め込みモデル・チャンク設定・解析器のバージョンを `contents` に記録し、設定が変わった内容を一括で再索引するコマンドを持つ（再解析は不要。保存済み DoclingDocument から作り直す）。

## 完了の確認

- E1. 評価用 PDF 7 件を API 経由で入庫し、全件 `ready` になる。
- E2. 各文書の見出しツリーが取得でき、表を含む文書（04）では表の子チャンクに表ヘッダが入っている。図を含む文書（05）では `figure` 子チャンクに図の説明が入っている（画像説明 有効時）。
- E3. 同じ PDF を別 KB にアップロードすると解析が走らず `skipped` になる。
- E4. Qdrant に子チャンク数と同じ数の点があり、各点が dense と bm25 の両方のベクトルを持つ。
- E5. 文書を削除→復元→削除→（保持期間を 0 にして）GC で、点・行・ファイルが消える。
