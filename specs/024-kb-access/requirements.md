# 024 部門とナレッジベースの利用範囲（提案・未承認）

> 状態: **承認済み（2026-11-09）**。Q1 は案 A、Q2 は「作らせる」。

## 1. 旧版との比較と、旧版の分かりにくさ

旧版（a-rag）は部門（team）と `kb_grants(kb, user/team/org, read/write)` を持っていた。機能は足りていたが、次の点で分かりにくかった。

| 旧版の分かりにくさ | 出どころ |
|---|---|
| KB に「種別（全社 / 部門）」と「付与の表」の 2 つの仕組みがあり、部門 KB は自部門に read が**暗黙に**付き、部門管理者は**暗黙に**書込・管理できた。画面の表に出ない権限がある | `kb.team_id`・`can_write_kb`・`kb-detail.tsx` の scope エディタ |
| 「部門 KB ⇄ 全社 KB」の移動（scope change）が付与の変更とは別の操作 | `kbs/[id]/scope` |
| 既定拒否で、付与を忘れると作った KB を誰も見られない | `share_with_scope` |
| 「この人は何を見られるか」「なぜ見られるか」を答える画面が無い | — |
| 個人への read 付与を途中で廃止し、部門外の人に 1 つの KB だけ見せることができなくなった | migration `698a4ea1ddc0` |

新版は今、個人 KB（本人だけ）と全社 KB（全員が閲覧・admin だけが書込）の 2 種類だけで、
全社 KB の閲覧者を絞れない・admin 以外が共有 KB に文書を足せない・共有スレッドから見る権限の無い引用が見える、の 3 つが困る。

## 2. 方針: 「暗黙の権限を持たない。すべて 1 枚の共有リストに出る」

Google ドライブの「共有」と同じ形にする。利用者が既に知っている形なので説明が要らない。

- 共有 KB には **共有リスト** が 1 枚だけある。各行は「**誰に**（全員 / 部門 / 人）× **何ができるか**（閲覧 / 編集 / 管理）」。
- 権限はこのリストの行から**だけ**来る。部門 KB という種別、部門管理者の暗黙の書込、scope の移動は作らない。
  （例外は admin だけ: どの共有 KB の共有リストも変更できる。→ 6 の Q1）
- 部門 KB は「共有リストが『製造部: 閲覧』の KB」のことで、特別な種類ではない。全社に広げるのは行を「全員」に変えるだけ。

## 3. 部門

- R1 部門: 名前・メンバー。1 人が複数の部門に入れる（兼務）。入れ子にはしない（階層は運用が重く、今は要らない）。
- R2 部門のメンバーの役割は **メンバー** と **部門管理者**。
  - 部門管理者ができるのは、自部門のメンバーの追加・削除と、自部門向けの KB の作成（4 の R9）。それ以外の権限は付かない。
  - 部門の作成・名前変更・削除・部門管理者の指名は admin。
- R3 人を部門から外すと、その部門経由の権限はすぐに無くなる（次の検索から効く）。

## 4. 共有 KB の共有リスト

- R4 役割は 3 段階で、上は下を含む。
  - **閲覧**: 文書の閲覧・検索・質問の範囲に入る。
  - **編集**: 文書・フォルダの追加・名前変更・移動・削除（＋閲覧）。
  - **管理**: 共有リストの変更・KB の名前変更・アーカイブ・削除（＋編集）。
- R5 行の「誰に」は **全員**（社内の全員）・**部門**・**人** の 3 種類。1 人に複数の行が当たるときは、いちばん強い役割になる。
- R6 「全員」には閲覧だけを付けられる（全員に編集を付ける事故を防ぐ）。
- R7 KB に「管理」が 1 行も無い状態は作れない（admin が作った KB は作った admin が管理になる）。
- R8 共有リストを狭める（行を消す・役割を下げる・「全員」を外す）ときは、**見られなくなる人数と名前**を出して確認する。
- R9 作るときの既定:
  - admin が作る: 「全員: 閲覧」「作った人: 管理」。
  - 部門管理者が作る: 「その部門: 閲覧」「作った人: 管理」。
  - 作った直後に共有リストを開き、誰に見えるかを確かめられるようにする。
- R10 個人 KB は今のまま（本人だけ。共有リストは持たない）。

## 5. 「誰が見られるか・なぜ見られるか」を答える画面

- R11 ライブラリの見出しに、共有リストの要約を 1 行で出す（例「製造部・品質保証部 ほか 2 名が閲覧 · 編集 3 名」）。押すと共有リストを開く。
- R12 共有リストで、部門の行を開くと、その部門の人の一覧が出る。リストの下に「閲覧できる人: 合計 n 名」を出す。
- R13 admin の「メンバー」画面で人を開くと、その人が見られる共有 KB と**理由**（「製造部のメンバーとして閲覧」「本人に編集」など）を出す。
- R14 サイドバーの KB 行の印は、全員に公開か（印なし）・限られた人だけか（鍵）・自分が閲覧だけか（今の「閲覧のみ」）。

## 6. 判断が要る点

- **Q1 admin は、自分が共有リストに無い KB の中身を見られるか。** → **決定（2026-11-09）: 案 A**
  - 案 A（採用）: 見られない。admin は共有リストの変更（自分を足すことも含む）はできるが、それは監査に残る。人事資料などを admin からも隠せる。旧版と同じ。
  - 案 B: admin は全部見られる。単純だが、admin に見せたくない資料を置けない。
- **Q2 部門管理者に KB を作らせるか（R9）。** → **決定（2026-11-09）: 作らせる** 作らせない場合は admin だけが作り、部門管理者は「管理」を付けてもらって運用する。

## 7. 一緒に直すこと

- R15 権限の判定は `kb/permissions.py` と `search/scope.py` に集める。一覧・文書・検索・質問の範囲・引用・概要（specs/023）がすべて同じ判定を通る。見えない KB は今どおり 404。
- R16 共有スレッドを開いた人が引用先の KB を読めないときは、その引用の本文・文書名を出さず「閲覧権限のない資料」と出す。
- R17 監査: `department.create/rename/delete`・`department.member_add/member_remove/role`・`kb.share_add/share_change/share_remove`。
- R18 退職処理（個人 KB・スレッドの扱い）・所有者の移譲は別の仕様にする。退職させた人は部門と共有リストの行から外す（R3 と同じ扱い）。

## 8. データ（案）

- `departments(id, name, created_at, deleted_at)`
- `department_members(department_id, user_id, role: member|manager)`
- `kb_shares(kb_id, subject_type: everyone|department|user, subject_id NULL 可, role: viewer|editor|manager)`、`(kb_id, subject_type, subject_id)` で一意。
- 今の全社 KB は移行で「全員: 閲覧」を、admin 全員に「管理」を付ける（今の見え方を変えない）。
- 検索の範囲は `kb_shares` を 1 回の SQL で引き、自分の部門の id と自分の id に当たる行がある KB に絞る。
