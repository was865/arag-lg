# 024 ナレッジベースの利用範囲（提案・未承認）

> 状態: **提案**。利用者の判断待ち。実装はまだしていない。

## 旧版との比較（要点）

旧版（a-rag）は `kb_grants(kb, user/team/org, read/write)` で KB ごとに閲覧・書込を付け、部門（team）と部門管理者があった。
新版は「1 デプロイ = 1 社」で、KB は個人（本人だけ）と全社（全員が閲覧、admin だけが書込）の 2 種類だけ。

新版で困ること:

1. **全社 KB の閲覧者を絞れない。** 人事・経営・顧客別の資料は、全員に見えてよい KB にしか置けない。
2. **admin 以外は共有 KB に文書を足せない。** 部署の担当者が自分の部署の資料を更新できない。
3. **共有したスレッドから、見る権限のない資料の引用が見える。** スレッドの共有範囲「社内」は、引用先の KB の閲覧権を見ていない。
4. 退職処理（個人 KB・スレッドの扱い）・所有者の移譲が無い（P5 予定のまま）。

旧版の付与表は自由度が高い反面、「誰が何を見られるか」を 1 画面で答えにくく、既定拒否（付与が無ければ見えない）で
「KB を作ったのに誰も見えない」事故が起きやすかった。部門の表を持つと、人事異動の保守も要る。

## 提案（旧版より単純にして、困りごと 1〜3 を解く）

- P1 全社 KB に「公開範囲」を持たせる: **全員**（今と同じ・既定）か **メンバーだけ**。
- P2 KB ごとに **メンバー**（利用者 × 役割）を持つ。役割は **閲覧** と **編集**（文書・フォルダの追加・変更・削除）。
  - 公開範囲が「全員」の KB でも、編集メンバーを付ければ admin 以外が文書を足せる（困りごと 2）。
  - KB の名前変更・アーカイブ・削除・メンバーの変更は admin だけ（今と同じ）。
  - 部門（team）は作らない。人の集合が要るようになったら、メンバーにグループを足せる形にしておく。
- P3 admin は「メンバーだけ」の KB の存在とメンバーを管理できるが、メンバーでなければ中身を検索・閲覧しない
  （旧版と同じく、管理と閲覧を分ける）。※ admin には全部見せる、という選択肢もある。
- P4 権限の判定は今の `kb/permissions.py`・`search/scope.py` に寄せる（検索・一覧・文書・引用・概要がすべて同じ判定を通る）。
  見えない KB は今と同じく 404。
- P5 共有スレッドを開いた人が、引用先の KB を読めないときは、その引用の本文・文書名を出さず「閲覧権限のない資料」と出す（困りごと 3）。
- P6 監査: `kb.visibility`（公開範囲の変更）・`kb.member_add` / `kb.member_role` / `kb.member_remove`。
- P7 画面: ライブラリの見出しに公開範囲の印（全員 / メンバーだけ）。admin 向けに KB の「メンバー」パネル（メールで追加・役割・外す）。
  範囲を狭める（全員 → メンバーだけ）ときは、見えなくなる人数を出して確認する。

退職処理・所有者の移譲（困りごと 4）は別の仕様に分ける。
