# デモの台本: 文書と本物の ERP（Odoo）をまたぐ質問（specs/033 R25）

見せたいこと: ARag は文書（ある時点の記録）と社内システム（今の値）を区別して答え、
どちらの値をいつ取ったかを画面で示す。作った動きは無く、時刻・状態・差はすべて本当のもの。

## 準備（5 分）

```bash
make up                       # ARag 全体（3100）
make erp-reset && make up-erp # Odoo をスナップショットに戻し、erp-mcp を ARag に登録（ERP_TODAY は空＝今日）
make up-mock                  # 名簿・保全・課題
```

- KB は harukaze_plant（`uv run python -m arag.eval ingest --suite harukaze_plant`）。質問する人は購買課の所属（仕入単価が見える）。
- Odoo の画面（http://127.0.0.1:8069、admin）を別のタブに開いておく。

## 流れ（10 分）

1. **入力欄の札**: 「社内システム ●●●●」。札に触れると、システムごとの状態（応答あり・遅い・止まっている）と確かめた時刻。
2. **時点の違い**: 「10月末の部品台帳と今とで、軸受 6208ZZ の在庫はいくつ違いますか？」
   - 問い合わせ中は「ERP（Odoo） に問い合わせ中: get_stock part=6208ZZ ・3 秒」と秒が進む。終わると「ERP・1 行・0.6 秒」。
   - 回答の下の「時点の比較」: 台帳（10/31）47 個 と ERP（取得の時刻）45 個。
3. **今の値は動く**: Odoo の画面で軸受 6208ZZ（P-5010）を 2 個払い出す（在庫 → 移動 → 新規、検証）。
   ARag の出典の面で「最新にする」→「1 か所が変わりました」「現在庫 45 → 43 ↓」。回答の文は変わらず、
   「詳細」のシステムの処理に「社内システムを最新にした」が増える。取得の時点は「12 秒前」と進み続ける。
4. **文書の古い記述**: 「資材管理の手引きにある発注の問い合わせ先の内線番号は、今も正しいですか？」
   → 手引きは 2201、名簿は 2210（conflicts.yaml の c1）。
5. **権限**: 製造課の人で「軸受 6204ZZ-C3 の発注の仕入単価を教えてください。」→ 単価の列は伏せられ、その旨を答える。
6. **止まったとき**: `docker compose --profile erp stop odoo` → 札が「ERP 止まっている」に変わる（30 秒以内）。
   質問すると、ERP を使えなかったことを記録に残し、文書で答えられる部分だけを答える。`docker compose --profile erp start odoo` で戻す。
7. **管理画面**: 「社内システム」→ ERP の「呼び出し」。直近 1 時間の回数・失敗の率・p50/p95 と、最近の呼び出し（「最新にする」を含む）。

## 試走の記録（2026-11-20、Odoo・ERP_TODAY は空・gemma4-12b）

- 2: 台帳 47 個・ERP 45 個（11月20日取得）、差 2 個。時点の比較の表が出る（直す前は「45個（2026年11月20日取得）」の
  括弧の中の「20日」を値と取り違えて表が出なかった。`compare.ts` で括弧の中を値にしないようにした）。
- 3: 「最新にする」で「2 か所が変わりました」（現在庫 45 → 43、最後の入出庫が 11-20 棚卸 -2 に）。Odoo の画面の代わりに
  admin の RPC で棚卸の調整をした（`make erp-reset` で戻る）。
- 6: Odoo を止めても erp-mcp は生きていて ping が通るため、札が「応答あり」のままだった。呼び出しで「Odoo に接続できない」と
  分かったら死活の記録に書き（`McpRun.on_health`）、札は回答の終わりに読み直すようにした。回答は「接続できず確かめられなかった」と書く。
- 7: 直近 1 時間 62 回・失敗 4 回（6.5%。評価の権限の拒否）・p50 53 ms・p95 363 ms。
- まだ気になる点: 差し戻す前の下書き（誤った表など）が書き直しまでの 10 秒ほど画面に見える。在庫の報告の各シートの件数は、
  検索で拾った行だけを数えて少なく答える（11月16日は本当は 50 件）。
